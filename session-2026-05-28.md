## 1. Why this tool exists (the real problem)

The previous keep-alive approach did a lightweight **REST `GET` ping** — and Supabase **paused the project anyway**. Supabase tightened their definition of "activity": a read ping no longer counts. This tool does a real **`INSERT`** (a write), which is undeniable database activity. That write is the actual fix.

How the tool works: on a schedule it INSERTs a random row into a dedicated keep-alive table in each project, counts the rows, and deletes a random row only once a table exceeds 10 rows. Runs serverless on GitHub Actions — no local Python execution needed.

**Rule going forward:** this is a *standalone* watcher repo. Do **not** merge it into the app repos — it watches the projects from the outside.

## 3. How the config schema works (learned from reading the code)

`config.json` is a JSON **array**; each entry is one project with four fields:

- `name` — human label, used in logs only.
- `supabase_url` — `https://<project-ref>.supabase.co` (grab from **Project Settings → Data API → Project URL**; no trailing slash, no path).
- `supabase_key_env` — the **name** of the env var holding the key (the secure pattern). The insecure alternative `supabase_key` puts the raw key in the file — we did **not** use it.
- `table_name` — defaults to `KeepAlive` if omitted.

**What the script does to each project** (`main.py` → `services/supabase_service.py`):
1. Inserts a row `{ "name": <random 10-char string> }`.
2. Counts rows (`select('*', count='exact')`).
3. If count > 10, deletes one random row by `id`.

**Therefore the table needs at least:** an `id` (auto-increment primary key, used by the delete) and a `name` text column (used by the insert).

**The naming gotcha (critical):** the script passes `table_name` to Supabase **exactly as written, case-sensitive**. Postgres folds unquoted identifiers to lowercase, so a mixed-case name like `KeepAlive` would require `CREATE TABLE "KeepAlive"` (quoted), and a hyphenated `keep-alive` *always* needs quotes. Mismatch between config and DB is the #1 silent failure. We sidestepped it entirely by using plain lowercase `keepalive`.

## 5. The table SQL (run in BOTH projects' SQL Editor)

```sql
create table keepalive (
  id bigint generated by default as identity primary key,
  name text default '',
  random uuid default gen_random_uuid()
);
```

- `id` + `name` are the two columns the script needs; `random` is optional/harmless.
- No seed rows — so each table started **empty** (0 rows), which made verification unambiguous.
- Because we use the `sb_secret_` key (bypasses RLS), **no RLS policies needed** on this table.

## 7. The exit-code fix (so failure alerts actually work)

**Problem found:** `main.py` caught every Supabase error (returning `False`) and the process still exited `0`. So a failed insert produced a **green** run — meaning GitHub's built-in "email on failure" would *never* fire for the one thing we care about.

**Fix applied to `main.py`:**
- Added `import sys`.
- `main()` now `return all_successful` (and the early config-error paths return falsy).
- Entry point changed to `sys.exit(0 if main() else 1)`.

Now a real failure turns the run **red**, which is the trigger GitHub's failure email watches for. Also trimmed `keep-alive.yml`'s `env:` block from `SUPABASE_KEY_1..5` down to just the two keys actually in use.

## 8. Failure notifications

- **Built-in (chosen, simplest):** GitHub emails on red runs. Enable in **personal Settings → Notifications → Actions** → turn on **Email** and tick **"Send notifications for failed workflows only."**
- **Scheduled-run nuance:** GitHub sends *cron* failure emails to whoever **last edited the workflow file**. On a fork that's the upstream author by default, so we trimmed `keep-alive.yml` (section 7) partly to make **ahmedmusawir** the last editor and therefore the recipient.
- **Heavier option (declined):** a Slack/Discord/email-action step — overkill for two projects, needs another secret.

## 9. The 60-day disable + the monthly heartbeat

**The concept:** GitHub **auto-disables scheduled workflows after 60 days of no repository activity**. Crucially, a scheduled workflow merely *running* does **not** reset that 60-day timer — only **commits/pushes** do. So the twice-weekly keep-alive keeps *Supabase* awake but does nothing to keep *GitHub's scheduler* awake.

**Why monthly, not 60-day:** 60 days is the *deadline*, not the interval. The heartbeat must fire comfortably *before* the deadline with margin, so it runs **monthly (1st of each month)** — it resets the 60-day clock roughly twice over before it could ever expire.

**`.github/workflows/heartbeat.yml`** (added this session): on `cron: '0 0 1 * *'`, it writes a UTC timestamp into a `.heartbeat` file, commits it as `github-actions[bot]`, and pushes. That commit is the real repo activity that resets the clock. Needs `permissions: contents: write`; gated by the same `ENABLE_GITHUB_ACTIONS` switch.

## 14. How to change things later

- **Change which days the keep-alive runs:** edit the `1,4` in `keep-alive.yml`'s cron (`0`=Sun … `6`=Sat). Tell Claude the days.
- **Add a 3rd project:** (1) add an entry to `config.json` with a new env name, e.g. `SUPABASE_KEY_3`; (2) add a matching repo Secret; (3) add a `SUPABASE_KEY_3: ${{ secrets.SUPABASE_KEY_3 }}` line to `keep-alive.yml`'s `env:`; (4) create the `keepalive` table in that project.
- **If the keep-alive ever shows red:** read the *Run keep-alive script* log. "Skipping… URL or Key missing" = secret name mismatch; insert/auth error = wrong key (publishable instead of `sb_secret_`, or wrong project's key); job "skipped" = `ENABLE_GITHUB_ACTIONS` not exactly `true`.
- **Keep the heartbeat working:** don't disable Actions; the monthly commit must be allowed to push (write permission — already confirmed OK).
